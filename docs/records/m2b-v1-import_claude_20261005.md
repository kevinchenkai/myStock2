## 做了什么

- **只读**：以 `mode=ro` + `query_only` 打开 V1 库；测试验证 V1 库文件字节不变、连接不可写；校验必须具备 V1 的四张表才继续。
- **成交 → FILL**：规范键与 Futu 直采**相同**（不含来源），同一笔成交跨通道自然归并并补证据链接；缺 `deal_id` 的进待匹配队列；缺字段/非 HK·US 代码的跳过并逐条报告；与已有事件**经济字段**冲突的逐条报告而不合并。
- **精度**（LG-08）：V1 的 REAL 无法还原十进制原文，价格按 4 位、数量按 6 位小数量化，**逐笔统计量化舍入差**（报告 `max_price_rounding`、`total_notional_rounding`）。
- **时区**：V1 时间是交易所本地时间且无时区标记，按市场补 IANA 时区（含夏令时与毫秒），事件备注标 `tz_inferred`。
- **日快照**：V1 `positions`/`account_funds` → `account_snapshot`（仅有日期：`captured_at` 取当日 23:59:59Z，source=`v1-date-only`；现金按 HKD/USD 拆分，持仓含券商成本）。
- **缺口如实**：报告列出 `fees_not_in_v1`、`cash_flows_not_in_v1`、`dividends_not_in_v1`、`account_id_not_in_v1`、`timezone_inferred`——**不凭空补出**；开账日前历史仅作描述（账本既有规则）。
- CLI：`python -m mystock2 v1 import --v1-db PATH --account-id ID [--dry-run]`（先 dry-run 看报告）。

## 一并修复的真实问题（M2b 暴露）

**账本内容哈希过严**：不同来源渠道对同一业务事件常带不同辅助元数据（订单号、备注），原实现把它们算进内容哈希，会把跨通道重复误报为冲突。现改为**只对经济字段**（类型、时间、标的、币种、价、量、现金、应收等）求哈希；辅助元数据保留首次写入者的，重复到达不覆盖。经济字段不同仍报冲突（有测试）。ADR 0001 的决定 3 随之补充。

## 偏差与说明（如实）

1. `account_id` 须由调用方显式给出；它必须与将来 Futu 采集使用的账户标识**一致**才能去重——这需要在 M0b/M2a 授权后确认券商主体与 `acc_id`（D10）。
2. 订单（`orders`）**不导入**为账本事件（订单是意图，撤单/失败不产生事件）；订单号只作为成交的辅助引用。
3. 导入后账本现金只来自成交（无入出金/股息/费用），与券商快照**不可能对齐**——这是 V1 数据缺口，不是导入缺陷；对账以开账日起的前向数据为准。
