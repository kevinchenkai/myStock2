## 1 摘要

**要做什么。** 一个单用户、本地运行的港美股系统：随时看清账户（Web），每天对圈定标的给出下一交易日**操作单**（教练），并在同口径下公平比较「人类 / AI / 买入持有」（记分牌），逐笔复盘人类操作。

**为什么新建仓库而不是改 V1。** V1 已能采集、展示、预测区间，但两份项目书独立得出相同结论：它**不能公平回答「AI 是否比我赚得多」**——账本无费用与资金流水、人类基线被重新撮合、各策略资金口径不一、没有带数量与有效期的操作单。这些是数据模型层面的问题，在 V1 上补丁会牵动全部页面与 ML 管线；V2 以**账本优先**重建数据地基，V1 保持原样运行、只读保留。

**本方案相对两份项目书新增或修订的要点（评审时请重点挑战）：**

1. **关键路径是「前向观察时钟」，而且只有满足完整证据协议的记录才计入。** 统计功效检验表明小优势需数百至数千交易日才能识别（§2.3）；前向样本无法靠算力或 agent 数量加速。里程碑据此排序，并拆出**最小前向包**（行情归档、线内状态、结构化意图、协议冻结、冻结与评分 CLI），不等全量历史导入与完整 Web（§4）。朴素基线线的观察期**不能替代**后续模型线的观察期。
2. **三条证据路径，三种引擎，不合并成一个「打败人类 x%」（v0.2 修订，gpt R01）。**
   ① `human_actual`：真实成交原样记账——事实与执行诊断，**描述性**；
   ② `human_plan`：用户**事前**记录、结构化（动作/限价/数量/有效期/是否已看 AI）的人类计划，与 AI 经过**同一套**预算、撮合、结算规则的模拟——**正式比较的人类对照**；
   ③ `live_guidance`：对真实账户状态生成的指导单，只做展示与执行验证。
   若用户不愿记录结构化人类计划，则结论**只能**限定为「模拟策略与实际账户的描述性比较」（D12）。
3. **每条策略线只读自己的状态（v0.2，R03）。** 公共预测可共享，真实账户库存**不得**注入模拟线；每张操作单留档 `state_ref` 与状态哈希。
4. **新线以「比较批次」加入（v0.2，R04）。** 新候选线（如 LightGBM+CQR）在同一天以与对照线**相同的初始现金、库存与估值**起跑，按共同窗口报告；旧线长期记录保留，不与新线拼接成一个证明。
5. **从第一天起就是「视图即模块」。** 绿地仓库没有迁移负担，视图框架（Claude 稿 P5）提前到 M3。
6. **首条 AI 线用透明基线预测器**（V1 `naive_vol` 思路），先打通「预测→操作单→冻结→记分」全链路；LightGBM+CQR 作为后续候选线（M8）。**G5 的范围裁决**（原始需求写的是「用最先进大模型独立建模预测」）：首期为「数值预测＋账户约束＋LLM 否决」，**独立 LLM 预测路径延后为 challenger**，待负责人确认（D7、D13）。

**成功的两层定义**（沿用两稿）：A 工程成功（确定性、必须通过）；B 策略成功（概率性、允许「证据不足，继续观察」）。

## 2 输入综合

### 2.1 两份项目书的一致点（直接采纳）

| 主题 | 共识 |

### 2.3 统计功效：决定了项目节奏

沿用 Claude 稿 §7.5 的估算（σ=1% 为假设，M0 用真实数据重估）：真实日均优势 5 bps 需约 3,100 个交易日、10 bps 约 780、20 bps 约 200 才能在 5% 显著、80% 功效下识别。含义：

- **A 层（工程）必须通过；B 层（策略）大概率长期停在「继续观察」**，这是正常结果，不是失败。
- 同时盯**过程指标**（操作单覆盖率、预测校准、成交假设稳定性）与经济意义；任何单个收益数字都不当作证明。
- 前向观察日数无法加速 → **越早冻结第一条合格线越好**（§4 关键路径）。
- 上表只是示意（独立同分布近似）：实际配对差有持仓延续、厚尾与相关性；σ 与有效样本量须用**同协议**的开发期回放或前向先导样本估计，并做块长度与最小可检测效应的敏感性分析。60/120 日是运行下限与评审时点，**不是功效保证**。

## 3 关键架构决定

### 3.1 V2 与 V1 的关系（待 D0 确认）

| 项 | 决定 |
| --- | --- |
| 仓库 | V2 独立仓库（本仓库）。V1 `kevinchenkai/myStock` 保持运行与只读，**V2 不修改、不重启、不写入 V1** |
| 数据 | V2 自建数据库 `data/mystock2.db`。V1 `data/mystock.db` 通过**一次性、只读**导入器进入 V2 账本（`collectors/v1_import`），导入前后做校验；导入器只开 `mode=ro` 连接 |
| 代码复用 | **拷贝＋重写测试**，不 `import` V1。优先拷贝：`code_map`（富途↔yfinance 代码映射）、Futu/yfinance 采集客户端的分段与重试逻辑、交易日历、LightGBM+CQR 预测器（M8）。每个拷贝文件头注明来源提交 SHA |
| 环境 | 新 conda 环境（默认 `mk2`、Python 3.11，D9），不污染 V1 的 `mk` |
| 并行期 | V1 的 `update.sh` 仍可由用户照常运行；V2 采集独立进行，二者互不依赖。对账期可对比两边持仓数。**V1 与 V2 共用同一富途账户与 OpenD**，接口额度（如历史成交每 30 秒 ≤10 次）与连接数是共享资源：M0 核验并发影响，V2 采集默认错峰、限频 |
| 跨通道去重 | 同一笔成交可能经 V1 导入、Futu 直采、CSV 三条通道到达；规范事件键与原始来源证据**分开保存**（§6），避免重复记账 |

### 3.2 技术栈

Python 3.11 · Flask（只读 Web）· SQLite（WAL，Web 用 `mode=ro` URI 连接）· Decimal 全程 · pytest · 前端沿用静态 JS＋`lightweight-charts`（本地 vendor，不走 CDN）· 配置 YAML · 命令行 `python -m mystock2 <子命令>`（或薄 shell 封装）。LLM 层仅 JSON schema 校验的文件通道（M9）。不引入 React/FastAPI/PostgreSQL/消息队列。

### 3.4 依赖与边界（由测试强制）

```
core ← instruments ← collectors
core ← ledger（只依赖 core、instruments）
core ← market
ledger, market, forecast → coach → scoreboard
```

- 一个 `tests/test_import_boundaries.py` 扫描 import 图，违反即失败（**M1 交付**）。
- 写库只发生在 `collectors / ledger / coach / scoreboard / replay / assistant(importer)` 的 CLI 路径；Web 进程用只读连接，写操作会被 SQLite 拒绝（有测试）。
- **import 图不足以保证「研究不改账户事实」**（v0.2，R19）：每个写入模块通过**写表登记表**打开连接，并用 `sqlite3.Connection.set_authorizer` 拒绝对非本模块所属表的写操作（`forecast`、`assistant` 等研究类模块对 `ledger_*` 没有任何写权限）。是否进一步拆成多个库文件由 M1 的 ADR 决定。测试：研究/assistant 连接尝试更新账本必败；Web 的**所有路由**集成测试断言无写入、无外部请求、无训练调用。

- 忽略（`.gitignore`，`config/local/` 将在 M1 补入）：`config.yaml`、`config.*.local.yaml`、`config/local/`、`data/`、`*.db*`、`exports/`、`backups/`。
- **真实的** universe（标的、`max_weight`、`max_lots`）、冻结协议（预算 `B`、开账日、参数）与费用档案**属私有配置**，只存本地 `config/local/`；公开仓库只含模板和合成值。需要公开时发布**白名单摘要**，并登记摘要哈希与私有完整包的本地引用（v0.2，R16）。

## 4 里程碑与关键路径

### 4.1 排序原则

1. 先**可信的账户事实**（M2a 最小前向包），因为所有比较都依赖它；但**不等全量历史导入**。
2. 然后以最短路径**冻结第一条合格线并开始前向计时**（M4–M6）。「合格」= 满足 §7 的完整证据协议（输入时点可证、线内状态、结构化人类计划、执行协议已冻结）。
3. 用户可立即使用的 Web（M3）与前向包**并行**，兑现目标 1，但不阻塞 M6。
4. 复盘卡、LLM、更强预测、近实时、V1 历史导入不在关键路径上，可与前向观察期并行。

**最小前向包（M6 的硬依赖）**：行情与证据归档（M4）· 线内状态与保守撮合（M5）· 结构化意图/人类计划最小 CLI（M6）· 协议冻结（M6）· 操作单冻结与评分 CLI（M5/M6）· 开账日快照与向前成交采集（M2a）。**不含**：V1 全量历史导入（M2b）、完整 Web 视图（M3）、复盘卡（M7）。

```
M0a(源码/文档只读预审) ─ M0b(DB 审计/备份) ─ M1 ─ M2a(最小账本) ─┬─ M3 Web ─────────┐
                                                               ├─ M2b V1 历史导入   │
                                                               └─ M4 ─ M5 ─ M6 ★ ─┬─ M7 复盘
                                                                                 ├─ M8 候选线(新批次)
                                                                                 ├─ M9 LLM 否决(新批次)
                                                                                 └─ M10 近实时 / 交接
```

★ = 合格前向观察开始累计。**各线各有观察起点**（基线线、`ai_lgbm`、`ai_veto` 不跨线累计样本）。每市场 ≥60 个计划日为运行下限，≥120 个交易日做一次**预先固定的**评审（§7）。

最终字段由各里程碑的 ADR 固定（`docs/adr/`）。下表是**表清单与所属里程碑**（以 §4.2 里程碑表为准）；DDL 在对应里程碑评审。

| `ticket` | M6 | 冻结后不可改；`kind(line_sim/live_guidance)`、`line_id`、`state_ref`、`frozen_hash`、`supersedes`；原因码与作废条件；选择规则标记 |
| `intent` | M6 | **结构化人类计划**：动作、限价、数量、有效期、`seen_ai`、真实记录时间、决策前 vs 事后补录；不可改写 |
| `llm_call` / `veto_packet` | M9 | 提供方、实际模型 ID、prompt 版本、输入证据引用与哈希、输出、延迟、成本；包绑定批次/目标日/基础单哈希 |

**账本不变量（M2a 的单测与对账器依据）：**

1. 持仓数量 ＝ Σ（同一账户、标的）`qty_delta`；现金（逐币种）＝ Σ `cash_delta`。**期初状态以显式期初事件进入和式**，不存在和式之外的「期初余额」。
2. `FILL` 的 `cash_delta` 为不含费用的成交额；费用是独立 `FEE`/`TAX` 事件，可晚到并通过 `ref_deal_id` 归属。
3. **每一类现金变化只有一个记账来源**；其他来源用于对账，不重复入账。
4. 同一规范业务键的重复到达是幂等 no-op；内容冲突是错误并进入待处理队列。**不同来源渠道到达的同一业务事件归并为一个规范事件**。
5. 更正 ＝ 原子地追加 `REVERSAL`（取反旧效应）＋新事件；更正链不成环；旧行不改。
6. 外部资金流（`DEPOSIT/WITHDRAW`，及带外部流分类的 `ADJUST`）不进入收益；`FX` 两币种腿以 `group_id` 原子写入，缺一腿则整组不生效。
7. 可交易现金与可卖库存由 `settlement_state` 在经济现金与库存之上推导，不等同于 Σ。

## 12 多模型评审方案（gpt-6.1 · grok-4.7）

### 12.1 目的与原则

在编码前用两个独立模型对本方案做 double check。**独立**：两者互不看对方意见，且各自拿到同一份材料与同一份评审提示。**只出结论不改文件**。执笔方（Claude）逐条处置并留痕；分歧交项目负责人。

### 12.2 材料包（均已入库、不含私有数据）

必读：本方案；[Claude 项目书](../prd/mystock-project-v2_claude_20261003.md)；[Codex 项目书](../prd/mystock-project-v2_codex_20261003.md)；[原始想法](../V2项目%20idea.md)；[AGENTS.md](../../AGENTS.md)。参考：V1 `AGENTS.md`/`COLLABORATION.md`（描述性，不含数据）。

### 12.3 评审维度

1. **目标覆盖**：idea 的两大目标与 G1–G7 是否都有里程碑与验收；有无遗漏。
2. **正确性与自洽**：账本不变量、sleeve 协议、操作单字段、时点定义有无逻辑漏洞或泄漏（前视）风险。
3. **统计与证据**：功效估算、预注册、多重比较与搜索预算、前向观察长度是否合理；措辞是否越界。
4. **关键路径与排序**：§4 的「尽早启动前向时钟」是否成立；有无更优排序或应提前/延后的项。
5. **架构与可实施性**：目录、依赖边界、只读保证、迁移、与 V1 关系（D0）；是否过度设计或欠设计。
6. **安全与隐私**：密钥、私有数据、LLM 权限、公开仓库风险。
7. **金融/市场细节**：港美股交易日历、截止时间、lot/tick、拆股/股息、费用、汇率、富途接口限制是否有常识性错误。
8. **可测试性**：§8 反例是否充分；验收是否可执行。
9. **两稿合并的裁决（§2.2）**是否合理；有无被忽略的重要分歧。
10. **待决事项（§10）**：默认值与阻塞关系是否合理。

### 12.4 输出格式（要求两位评审一致）

按严重度分级，每条一行 JSON 或表格行：

`级别(must-fix/should-fix/nit) | 方案章节 | 问题 | 理由/反例 | 建议修改`

另给：① 总体结论（通过 / 有条件通过 / 不通过）与 3–5 句理由；② 最危险的 3 个假设；③ 你认为被遗漏的最重要的一项。**不得编造 V1 或接口的事实**：不确定处标「需核实」。

### 12.5 流程与收敛标准

1. 两位评审并行独立评审 → 产出各自评审文件（`docs/plans/plan-review_gpt_YYYYMMDD.md`、`plan-review_grok_YYYYMMDD.md`，作者标记按实际生成者）。
2. 执笔方逐条处置，写入 `docs/plans/plan-review-log_claude_YYYYMMDD.md`（采纳／部分采纳／不采纳＋理由），修订本方案并升版本号。
3. 评审分歧单列，交项目负责人裁决。
4. **收敛标准（D11）**：两位评审对修订版均无 must-fix，且项目负责人确认。必要时进行第二轮（只复核上轮 must-fix 与新增改动）。
5. 通过后在 `OPEN_ITEMS.md` 关闭 RV-01/RV-02。**M0a（只读预审）可在评审收敛后立即开始；M0b 及之后需相应授权。**
6. 评审进度：第一轮 gpt-6.1 已完成并处置（[评审](plan-review_gpt_20261005.md)、[评审记录](plan-review-log_claude_20261005.md)）；grok-4.7 待执行（本机 `grok` 命令行需用户先登录）；第二轮由 gpt-6.1 复核 v0.2 的 must-fix 处置与新增改动。

### 12.6 执行与隐私

发送内容仅限 §12.2 的已入库、已推送文档，不含私有数据。执行通道：gpt-6.1 经本机 Codex 客户端（只读沙箱、`--ephemeral`，评审方可联网查阅公开官方文档）；grok-4.7 经本机 `grok` 命令行，**需项目负责人先在终端完成登录**（执笔方不代为登录）。无法自动调用时，使用可直接粘贴的评审提示（[plan-review-prompt](plan-review-prompt_claude_20261005.md)）。评审结果**原文入库**并如实记录，包括负面意见；评审方引用的外部制度日期与链接由执笔方在 M0a 核实后才采纳。
