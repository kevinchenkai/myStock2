## 1 摘要

**要做什么。** 一个单用户、本地运行的港美股系统：随时看清账户（Web），每天对圈定标的给出下一交易日**操作单**（教练），并在同口径下公平比较「人类 / AI / 买入持有」（记分牌），逐笔复盘人类操作。

**为什么新建仓库而不是改 V1。** V1 已能采集、展示、预测区间，但两份项目书独立得出相同结论：它**不能公平回答「AI 是否比我赚得多」**——账本无费用与资金流水、人类基线被重新撮合、各策略资金口径不一、没有带数量与有效期的操作单。这些是数据模型层面的问题，在 V1 上补丁会牵动全部页面与 ML 管线；V2 以**账本优先**重建数据地基，V1 保持原样运行、只读保留。

**本方案相对两份项目书新增的四点（评审时请重点挑战）：**

1. **关键路径是「前向观察时钟」而非功能广度。** 统计功效检验表明小优势需数百至数千交易日才能识别（§2.3）；前向样本无法靠算力或 agent 数量加速。因此里程碑按「**尽早让一条冻结的、可记分的 AI 操作单流水线跑起来**」排序，复盘、LLM、近实时都排在其后（§4）。
2. **从第一天起就是「视图即模块」。** 绿地仓库没有迁移负担，视图框架（Claude 稿的 P5）提前到 M3，而不是「渐进迁入」。
3. **策略线（strategy line）是可增的注册表，不是写死的四个袋。** 新策略（如移植 LightGBM+CQR）以新线加入，从自己的起始日起算，**不重置已有线的观察时钟**（§6）。
4. **首条 AI 线用透明基线预测器**（V1 已有的 `naive_vol` 思路），先打通「预测→操作单→冻结→记分」全链路；LightGBM+CQR 移植为后续候选线（M8）。这样前向时钟在 M6 就开始，而不是等 ML 移植完。

**成功的两层定义**（沿用两稿）：A 工程成功（确定性、必须通过）；B 策略成功（概率性、允许「证据不足，继续观察」）。

### 2.1 两份项目书的一致点（直接采纳）

### 2.3 统计功效：决定了项目节奏

沿用 Claude 稿 §7.5 的估算（σ=1% 为假设，M0 用真实数据重估）：真实日均优势 5 bps 需约 3,100 个交易日、10 bps 约 780、20 bps 约 200 才能在 5% 显著、80% 功效下识别。含义：

- **A 层（工程）必须通过；B 层（策略）大概率长期停在「继续观察」**，这是正常结果，不是失败。
- 同时盯**过程指标**（操作单覆盖率、预测校准、成交假设稳定性）与经济意义；任何单个收益数字都不当作证明。
- 前向观察日数无法加速 → **越早冻结第一条线越好**（§4 关键路径）。

### 2.4 本方案不采纳或延后

| 内容 | 处置 |
| --- | --- |
| 自动下单、全市场选股、多用户、期权/杠杆/日内高频、离线 RL、HMM 软切换 | 范围外（沿用两稿非目标） |

## 3 关键架构决定

### 3.1 V2 与 V1 的关系（待 D0 确认）

| 项 | 决定 |
| --- | --- |
| 仓库 | V2 独立仓库（本仓库）。V1 `kevinchenkai/myStock` 保持运行与只读，**V2 不修改、不重启、不写入 V1** |
| 数据 | V2 自建数据库 `data/mystock2.db`。V1 `data/mystock.db` 通过**一次性、只读**导入器进入 V2 账本（`collectors/v1_import`），导入前后做校验；导入器只开 `mode=ro` 连接 |
| 代码复用 | **拷贝＋重写测试**，不 `import` V1。优先拷贝：`code_map`（富途↔yfinance 代码映射）、Futu/yfinance 采集客户端的分段与重试逻辑、交易日历、LightGBM+CQR 预测器（M8）。每个拷贝文件头注明来源提交 SHA |
| 环境 | 新 conda 环境（默认 `mk2`、Python 3.11，D9），不污染 V1 的 `mk` |
| 并行期 | V1 的 `update.sh` 仍可由用户照常运行；V2 采集独立进行，二者互不依赖。对账期可对比两边持仓数 |

### 3.2 技术栈

Python 3.11 · Flask（只读 Web）· SQLite（WAL，Web 用 `mode=ro` URI 连接）· Decimal 全程 · pytest · 前端沿用静态 JS＋`lightweight-charts`（本地 vendor，不走 CDN）· 配置 YAML · 命令行 `python -m mystock2 <子命令>`（或薄 shell 封装）。LLM 层仅 JSON schema 校验的文件通道（M9）。不引入 React/FastAPI/PostgreSQL/消息队列。

  scoreboard/  sleeve、matcher(保守撮合)、metrics、stats、lines(策略线注册表)
  replay/      cards、behavior、intent

  web/         app、views/<view_id>/{view.yaml,query.py,panel.js}、static

### 3.4 依赖与边界（由测试强制）

```
core ← instruments ← collectors
core ← ledger（只依赖 core、instruments）
core ← market
ledger, market, forecast → coach → scoreboard
web：只读依赖 ledger/market/coach/scoreboard 的 query 层，不 import forecast 训练代码
forecast 不 import web；assistant 不 import ledger 写接口
```

- 一个 `tests/test_import_boundaries.py` 扫描 import 图，违反即失败（**M1 交付**）。
- 写库只发生在 `collectors / ledger / coach / scoreboard / replay / assistant(importer)` 的 CLI 路径；Web 进程用只读连接，写操作会被 SQLite 拒绝（有测试）。

### 3.5 数据与隐私布局

- 公开仓库：代码、`config/*.yaml`（不含私有数值，如费率由用户填 `config.yaml` 或本地费用档案导入）、合成 fixtures、文档。
- 忽略（已写入 `.gitignore`）：`config.yaml`、`config.*.local.yaml`、`data/`、`*.db*`、`exports/`、`backups/`。
- 费用档案的**费率数值**属私有配置，由用户在本地填写；仓库只含模板与合成测试值。
- 发往外部模型（评审、LLM 否决）的内容只含文档或脱敏摘要。

### 3.6 版本号

分别记录 `application_version`、`feature_version`、`model_version`、`strategy_version`、`protocol_version`。UI 升级不得写成模型晋级。

## 4 里程碑与关键路径

### 4.1 排序原则

1. 先**可信的账户事实**（M1–M2），因为所有比较都依赖它。
2. 然后**用户立刻能用到的 Web**（M3），兑现目标 1，并为后续页面打样。
3. 然后以最短路径**冻结第一条 AI 线并开始前向计时**（M4–M6）。
4. 复盘、LLM、更强预测、近实时都**不在关键路径上**，可与前向观察期并行。

```
M0 ─ M1 ─ M2 ─ M3 ──────────────┐
            └─ M4 ─ M5 ─ M6(★前向时钟开始) ─┬─ M7 复盘
                                            ├─ M8 LightGBM+CQR 候选线
                                            ├─ M9 LLM 否决（人工通道）
                                            └─ M10 近实时 / 公开导出 / 交接
```

M3 与 M4 在 M2 之后可并行（不同文件集合，不同时改同一批文件）。★ = 前向观察日数开始累计：每市场 ≥60 个计划日为观察下限，≥120 个交易日做一次晋级评审。

**账本不变量（M2 的单测与对账器依据）：**

1. 持仓数量 = Σ 同一账户、标的的 `qty_delta`；现金（逐币种）= Σ `cash_delta`。
2. `FILL` 的 `cash_delta` 为不含费用的成交额；费用是独立 `FEE`（或 `TAX`）事件，可晚到并通过 `ref_deal_id` 归属。
3. 同一 `event_id` 重复写入是幂等 no-op；内容不同的同 ID 写入是错误。
4. 更正 = 新事件（`corrects_event_id` 指向旧事件，冲抵或替换其效应），不改旧行。
5. 外部资金流（`DEPOSIT/WITHDRAW`）不进入收益；`FX` 在两个币种各记一边。

## 11 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 统计功效不足 | 小优势无法与噪声区分，易过度解读 | 预注册；经济意义＋风险＋稳健性并看；允许「继续观察」；措辞限定（不称「已证明因果优势」） |

## 12 多模型评审方案（gpt-6.1 · grok-4.7）

### 12.1 目的与原则

在编码前用两个独立模型对本方案做 double check。**独立**：两者互不看对方意见，且各自拿到同一份材料与同一份评审提示。**只出结论不改文件**。执笔方（Claude）逐条处置并留痕；分歧交项目负责人。

### 12.2 材料包（均已入库、不含私有数据）

必读：本方案；[Claude 项目书](../prd/mystock-project-v2_claude_20261003.md)；[Codex 项目书](../prd/mystock-project-v2_codex_20261003.md)；[原始想法](../V2项目%20idea.md)；[AGENTS.md](../../AGENTS.md)。参考：V1 `AGENTS.md`/`COLLABORATION.md`（描述性，不含数据）。

### 12.3 评审维度

1. **目标覆盖**：idea 的两大目标与 G1–G7 是否都有里程碑与验收；有无遗漏。
2. **正确性与自洽**：账本不变量、sleeve 协议、操作单字段、时点定义有无逻辑漏洞或泄漏（前视）风险。
3. **统计与证据**：功效估算、预注册、多重比较与搜索预算、前向观察长度是否合理；措辞是否越界。
4. **关键路径与排序**：§4 的「尽早启动前向时钟」是否成立；有无更优排序或应提前/延后的项。
5. **架构与可实施性**：目录、依赖边界、只读保证、迁移、与 V1 关系（D0）；是否过度设计或欠设计。
6. **安全与隐私**：密钥、私有数据、LLM 权限、公开仓库风险。
7. **金融/市场细节**：港美股交易日历、截止时间、lot/tick、拆股/股息、费用、汇率、富途接口限制是否有常识性错误。
8. **可测试性**：§8 反例是否充分；验收是否可执行。
9. **两稿合并的裁决（§2.2）**是否合理；有无被忽略的重要分歧。
10. **待决事项（§10）**：默认值与阻塞关系是否合理。

### 12.4 输出格式（要求两位评审一致）

按严重度分级，每条一行 JSON 或表格行：

`级别(must-fix/should-fix/nit) | 方案章节 | 问题 | 理由/反例 | 建议修改`

另给：① 总体结论（通过 / 有条件通过 / 不通过）与 3–5 句理由；② 最危险的 3 个假设；③ 你认为被遗漏的最重要的一项。**不得编造 V1 或接口的事实**：不确定处标「需核实」。

### 12.5 流程与收敛标准

1. 两位评审并行独立评审 → 产出各自评审文件（`docs/plans/plan-review_gpt_YYYYMMDD.md`、`plan-review_grok_YYYYMMDD.md`，作者标记按实际生成者）。
2. 执笔方逐条处置，写入 `docs/plans/plan-review-log_claude_YYYYMMDD.md`（采纳／部分采纳／不采纳＋理由），修订本方案并升版本号。
3. 评审分歧单列，交项目负责人裁决。
4. **收敛标准（D11）**：两位评审对修订版均无 must-fix，且项目负责人确认。必要时进行第二轮（只复核上轮 must-fix 与新增改动）。
5. 通过后在 `OPEN_ITEMS.md` 关闭 RV-01/RV-02，方可开始 M0 的实施工作。

### 12.6 执行与隐私

发送内容仅限 §12.2 的已入库文档。**发送前须向项目负责人确认**（COLLABORATION §5、§8）。执行通道取决于本机可用性：grok 命令行需登录；gpt-6.1 经 Codex 客户端。无法自动调用时，由本方案提供可直接粘贴的评审提示（`docs/plans/plan-review-prompt_claude_20261005.md`）。评审结果如实记录，包括负面意见。
